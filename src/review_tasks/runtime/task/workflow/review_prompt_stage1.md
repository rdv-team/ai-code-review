## Что делает стадия 1

Ты выполняешь первую стадию локального ревью BSL-кода задачи `{{TASK}}`. На этой стадии систематически просматривай видимые изменения, фиксируй полный реестр конкретных кандидатов на проверку и привязывай к каждому кандидату маршруты нормативных источников. Находки с решением `keep`/`drop`, рекомендации и публичные поля здесь не формируются — это работа стадии 2 (`review_prompt_stage2.md`).

**Материал ревью** — только BSL-блоки из файла `review_bsl.md` (раздел `## BSL-блоки`). Основной фокус — новые TARGET-строки в секциях `-- new bsl --`, особенно строки с префиксом `+`. Непомеченный контекст используй для проверки влияния изменения. Секция `-- old bsl --` нужна только для понимания замены и не содержит TARGET-ссылок. Не открывай файлы проекта, per-file diff-артефакты и не используй номера строк из вывода команд. Комментарии (`//...`) не считаются исполняемым кодом; в многострочных строках частью значения являются только строки с `|...`.

Открытая конструкция или граница области в конце видимого BSL-блока сама по себе не является дефектом. Не создавай кандидатов из чистой стилистики, абстрактных опасений или предположений, не привязанных к конкретным строкам. При сомнении между обоснованным кандидатом и преждевременным отклонением сохраняй кандидата для Stage 2.

### Полная инвентаризация кандидатов

Пройди видимый `-- new bsl --` систематически по всем двенадцати областям. Для каждого конкретного подозрения, которое можно обосновать видимым кодом, создай отдельного кандидата. Бери широко, а не выборочно: стадия 1 должна не пропустить потенциальный дефект, а стадия 2 одинаково глубоко проверит и подтвердит либо отклонит каждый кандидат.

Каждое независимое место — отдельный кандидат со своими `file`, `start_line` и `end_line`. Не схлопывай разные экземпляры одного паттерна и не ограничивайся одним примером, если подозрительная конструкция встречается в нескольких местах. Повтор одной `area` в разных кандидатах разрешён и ожидаем. Числовой квоты нет: сохраняй все обоснованные кандидаты.

Для каждого подозрения действуй строго в такой последовательности:

1. Не вызывай CLI при первой мысли: закончи проверку текущей функции или локально связанного блока.
2. Проверь, нет ли в текущем блоке потенциального нарушения, которое можно заметить только с учётом проектных стандартов, документации по индексам или правил использования БСП.
3. Определи точный `file` и минимальный значимый диапазон TARGET-строк, достаточный для последующей проверки.
4. Сформулируй нейтральное `observation`: наблюдаемый факт и направление проверки, а не готовый вердикт. Рекомендуемый формат: «Наблюдаемый факт. Проверить, может ли / гарантирует ли / выполняется ли…».
5. Немедленно вызови `review-tasks stage1-add-candidate` отдельным CLI-вызовом, прежде чем переходить к следующему участку, и привяжи релевантные нормативные источники через `review-tasks stage1-link-*`.
6. Продолжай систематическое сканирование; не накапливай кандидаты до конца анализа.

```powershell
review-tasks stage1-add-candidate `
  --area error_handling `
  --file "CommonModules/рдв_ИнтеграцияСКоннекторомExt/Ext/Module.bsl" `
  --start-line 4103 `
  --end-line 4106 `
  --observation "Результат разбора используется до проверки диагностики. Проверить, может ли функция вернуть Неопределено."
```

CLI сам назначает `candidate-N`, валидирует `file` и обе границы, нормализует сохраняемые значения и идемпотентно возвращает существующее имя для точного дубля.

### Нормативная проверка

Stage 1 **только выявляет кандидатов по видимому BSL**. Проверка применимости полного содержимого стандартов и нормативное подтверждение выполняются только на Stage 2.

* Если `candidate` следует из видимого BSL — сразу зафиксируй его и продолжай анализ.
* Не активируй skill `mcp-review-verification` и не вызывай MCP на Stage 1; подтверждение или опровержение candidate через внешние источники — работа Stage 2.
* Для поиска дополнительных кандидатов и точного `standard_hint` выбери в `_review_info/reference-catalog.json` только релевантную по `description`/`ids` запись и прочитай указанный в `path` файл относительно корня задачи целиком, например `<TASK>/dev-standarts/*.md`. Если карточка поднимает конкретный риск в видимом BSL, создай candidate и привяжи ID через `review-tasks stage1-link-dev-standard --candidate candidate-N --id <stdN|rdvN>`.

### Жёсткий фильтр candidate

НЕ создавай `candidate` для замечаний только об именовании, опечатках в идентификаторах, форматировании, читаемости, `magic number/date` или общем `quality/style`.

### Исправление ошибочного кандидата

Если до появления `_review_info/review_result_stage2.yaml` кандидат оказался записан по ошибке, удали только его:

```powershell
review-tasks stage1-remove-candidate --candidate candidate-N
```

Команда удаляет кандидата вместе с его подсказками. **ЗАПРЕЩЕНО** удалять обоснованного кандидата только из-за неуверенности в наличии дефекта: его должна проверить и при необходимости отклонить Stage 2.

После начала Stage 2 технически **запрещено** удалять кандидатов: сохрани его и зафиксируй соответствующий finding с `self_check.decision: drop`.

### Candidate-specific маршрутизация нормативных источников

`standard_hints` — карта маршрутизации дальнейшей проверки, а не доказательство нарушения. Каждая привязка относится к одному конкретному `candidate-N`:

- `dev_standard_ids` — релевантные идентификаторы `stdN`/`rdvN` из `dev-standarts/`;
- `platform_index_files` — релевантные файлы из `platform-database-indexes/` при подозрении на запрос или индекс;
- `bsp_files` — конкретные имена общих модулей БСП. Для распознавания имён читай `.agents/skills/mcp-review-verification/references/ssl-library-search.md`; не активируй skill и не выполняй описанный там MCP workflow на Stage 1.

Для привязки используй только узкие команды:

```powershell
review-tasks stage1-link-dev-standard --candidate candidate-N --id std648
review-tasks stage1-link-platform-index --candidate candidate-N --file platform-database-indexes/14-platform-indexes-information-registers.md
review-tasks stage1-link-bsp-file --candidate candidate-N --module ОбщегоНазначения
```

Для определения `--id` стандарта сначала выбери релевантную запись в `_review_info/reference-catalog.json`, затем прочитай указанный локальный `dev-standarts/*.md` полностью; не сканируй все Markdown ради поиска ID. Для `stdN` карточка остаётся routing hint до получения полного официального текста на Stage 2; для `rdvN` она является declared корпоративным источником. CLI хранит у каждого кандидата три списка подсказок; повторная привязка не создаёт дубль.
